# Agent Note: Electron desktop wrapper

Status: implemented

English | [中文](2026-08-13-electron-desktop-wrapper.zh.md)

## Problem

DeepSeek Harness exposes its graphical product through `dsh web`, which requires a terminal-managed server and a separate browser. A Windows desktop distribution must preserve the complete Host and browser behavior without depending on a source checkout, a separately installed Node.js runtime, or a fixed local port.

## Decision

`apps/desktop` is an Electron shell over the existing loopback Web carrier. Its main process holds Electron's single-instance lock, immediately shows a sandboxed and context-isolated preparation window, and starts the packaged `dsh web` backend through Electron's Node mode with the `--expose-internals` flag required by the HMR service and `--no-open` because Electron owns the only product window. The backend binds an operating-system-assigned loopback port. The preparation page uses DeepSeek's airy blue visual language, identifies DSH as the community desktop edition of DeepSeek Harness, and reports preparation through a two-stage timeline and stage-based progress bar. It remains responsive during extraction and connection, then transitions directly into the main Harness window when the backend becomes ready. The preparation page is replaced only after the backend prints its URL and an HTTP request returns successfully, so a URL printed immediately before a later Loader failure never becomes a broken navigation. A second launch focuses the existing window instead of starting another extraction or backend. Closing the application waits for backend termination and force-stops the owned process tree only when graceful shutdown does not reach quiescence.

The Windows installer carries the official `@deepseek-ai/dsh` production dependency closure as a gzip tar archive. The deployment-root manifest pins the published `@deepseek-ai/dsh` version instead of injecting the workspace member and explicitly roots the required workspace peers; pnpm deployment otherwise omits peer-only runtime imports. The workspace constraint permits the pinned CLI dependency while the [desktop runtime-closure decision](../bug-fix/2026-08-22-desktop-backend-runtime-closure.md) keeps the peer roots machine-checked. After deployment, staging replaces the deployed `@deepseek-ai/dsh-web-frontend` distribution and the desktop-modified client plugin bundles with the current checkout's just-built output, and copies the welcome artwork into the frontend assets. The published runtime closure remains intact while desktop renderer changes ship in the same installer. First launch extracts the archive atomically into the versioned Electron user-data directory because Electron Builder excludes nested `node_modules` from ordinary extra resources and Windows cannot safely recreate pnpm symbolic links without elevated link privileges. Extraction runs in a separate Electron Node-mode child process so archive work cannot block the browser-window event loop; the preparation page reports extraction, backend startup, and connection phases. The staging deployment uses pnpm's hoisted node linker so the archive contains real directories and native addon files. The application reuses an extraction only when its completion marker and every required runtime path exist; an interrupted or incomplete extraction is replaced before the backend starts. When a valid extraction is already present, the startup page identifies the fast path and states that the local environment is being reused instead of repeating first-run initialization copy.

This decision partially supersedes the Electron-specific IPC reservation in [GUI layering and the RPC protocol](../architecture/2026-07-19-gui-layering-and-rpc-protocol.md). The loopback carrier is the shipped desktop transport; an IPC carrier remains a compatible future optimization rather than a prerequisite for a desktop product.

The renderer receives an Electron-only Codex-inspired light skin after the backend page loads. The skin overrides design tokens and panel geometry without replacing Web components, so workspace, session, model, settings, composer, and details behavior remain owned by the existing Harness UI. The first-run surface uses DeepSeek's airy blue visual language, states that DSH abbreviates DeepSeek Harness, and identifies the community edition before model configuration. On Windows, Electron disables the native frame and application menu; a transparent drag region and app-owned minimize, maximize, restore, and close controls provide window behavior without reserving a visible title-bar row. The center and details column rules in `AppFrame.module.css` reserve a compact 30-pixel desktop-only top safe area while the sidebar remains flush with the window edge. Scoping the offset through the desktop body attribute keeps browser-hosted clients unchanged and lets CSS Modules bind the rule to the compiled column names. Standard text-editing shortcuts remain renderer behavior. The renderer root fills the entire client viewport, so the sidebar and main surface reach the bottom window edge. An isolated preload bridge exposes only single-directory selection and a fixed window-control action set to the renderer, and the main process accepts requests only from the owned window before opening Electron's native folder dialog or changing window state. Browser-hosted clients retain the existing Host picker. The community distribution is named DSH, uses the `@luo-ross/dsh-desktop` package and `io.github.luoross.dshdesktop` Windows application identity, and states that it is not an official DeepSeek AI product. Published installer and blockmap filenames include `Windows-x64` so the supported platform and architecture are explicit before download. Desktop workspace manifests point their source metadata to the community repository while every upstream release member retains the official repository URL. The DSH window keeps its product title after the upstream page loads. Its window, executable, installer, and Windows shortcuts use an ICO derived from the official DeepSeek whale mark at `apps/web/public/favicon.svg` instead of Electron's default mark.

Installed Windows builds use `electron-updater` with the public community GitHub Releases feed. The main process checks shortly after startup, again when the window regains focus after five quiet minutes, and every six hours while running, downloads stable updates in the background, and publishes progress through the narrow preload bridge. Every trigger shares one staleness clock, so whichever check finishes first suppresses the others until its freshness window expires. A compact action group at the content area's top-left always links to the community GitHub repository; its blue update action stays visible as the manual check control in idle states and switches to an immediate update action once a verified installer is ready. Electron's install-on-quit behavior is disabled, and a downloaded update remains pending across application exits and launches without interrupting work. Only clicking the ready control installs without a second confirmation. Update installation terminates the owned Harness backend, then runs the NSIS installer silently (`/S`) and relaunches the application after the install completes. Development and unpacked builds do not check the release feed. A release is update-complete only when its installer, `latest.yml`, and matching blockmap are published together.

## Alternatives considered

**Load the built Vite index directly.** The browser bundle is not a standalone application: `dsh web` injects its boot manifest and owns API and WebSocket routes, so `loadFile()` cannot provide the product.

**Implement an Electron IPC carrier first.** IPC could remove the loopback socket, but it would duplicate transport work before establishing desktop distribution. Reusing the security-fenced loopback carrier preserves current behavior and keeps the wrapper local to `apps/`.

**Package the deployed `node_modules` directory as ordinary extra resources.** Electron Builder filters nested dependency directories, and preserving pnpm links produces inaccessible links for ordinary Windows users. A single archive over a hoisted deployment is deterministic and keeps native addons on a real filesystem after extraction.

**Only link users to the newest installer.** A browser download remains the fallback for versions before updater support, but it leaves every later upgrade dependent on manual discovery and installation. The GitHub provider reuses the existing public release channel and generated NSIS metadata without adding an update server.

## Consequences

The desktop application reuses the entire Web surface and its settings, workspace, session, tool, and provider behavior. It binds only to `127.0.0.1`, chooses a free port, disables renderer Node integration, and opens external HTTP links in the system browser. The installer is larger than a remote-site wrapper, and first launch spends time expanding the bundled backend, but later launches reuse the versioned extraction. A backend version change creates a new extraction directory; uninstall-time cleanup of old version directories remains outside the wrapper's current lifecycle.

The verified Windows path builds the Harness, stages the production backend, receives HTTP 200 from the staged backend, builds the NSIS installer and update metadata, completes a fresh archive extraction, starts the packaged backend through Electron's embedded Node runtime, and presents the `DSH` window. Update delivery depends on GitHub availability. Unsigned releases retain checksum verification but can still trigger Windows unknown-publisher warnings during installation.
